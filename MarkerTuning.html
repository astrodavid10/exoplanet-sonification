Exoplanet Marker Tuning

Reference doc for the marker (dot) and reticle visuals used in exo-sonification.vue and exoplanet-renderer.ts. Section 1 documents the recent tuning pass. Section 2 explains how the current per-frame size formula works. Section 3 proposes a zoom-adaptive scaling change pending approval — not yet implemented.

1. Recent tuning changes

1.1 Dot sizes (exoplanet-renderer.ts:780-781)

Dot size is set in CSS px per mode and per device. The renderer multiplies by devicePixelRatio before uploading to the shader, and runs the result through the log-zoom formula in §2 to get the final pixel size.

ConstantMobile (coarse pointer)DesktopChange
DEFAULT_DOT_SIZE_2D 4 → 7 6 → 9 +3 px both — circles read clearly at typical FOVs
DEFAULT_DOT_SIZE_3D 2 → 1 4 (unchanged) Mobile only, ~2 device px reduction at typical DPR

Both values are overridable at runtime via window.__cloudDotSize (global) or window.__cloudDotSize2D / window.__cloudDotSize3D (per-mode) — useful for quick A/B without rebuilding.

2. How marker scale works today

The marker shader runs in screen space: every dot uploads a single pixel-size uniform per frame, so individual dots stay the same size regardless of where they sit in the world. This is the property we want to preserve. (Without it, a dot 10 kpc away would be 106× smaller than one in the solar neighbourhood and we’d see nothing.)

The pixel size is log-zoom adaptive today, but the calibration was inherited from a 3D-only era. The formula in exoplanet-renderer.ts:787-793 is: 

const sizeMin = sizeForMode;
const sizeMax = sizeForMode * 1.5;
const b = (sizeMax - sizeMin) / 10;   // = 0.05 · base
const a = sizeMax - b * 20;           // = 0.50 · base
sizeForMode = Math.round(a + b * Math.log(renderContext.viewCamera.zoom));
// ≡ base · (0.5 + 0.05 · ln(zoom)), rounded.

What the formula actually produces, given base:

So in both modes the current behavior runs opposite to what feels right perceptually. The §3 proposal flips the slope per mode and recenters the “1.0×” reference zoom so the default view matches the freshly-tuned base sizes from §1.

3. Proposal: zoom-adaptive scaling (awaiting approval)

Goal. Keep markers in screen space (no world-space sizing), but make the per-frame pixel size respond to camera zoom so that:
  • 2D: zooming in significantly (≈10° → 1°) grows the circle a little.
  • 3D: zooming far away from the field shrinks the dot; close-in stays at the §1 base.

3.1 Proposed formula

Replace the current a + b·ln(zoom) shape with a per-mode log-octave ramp that has a tunable reference zoom, a slope per octave, and explicit clamps. Pseudocode: 

function sizeForZoom(base, zoom, refZoom, slopePerOctave, minScale, maxScale) {
  const octaves = Math.log2(refZoom / zoom);   // +ve when zoomed IN relative to ref
  const scale = clamp(1 + slopePerOctave * octaves, minScale, maxScale);
  return base * scale;   // rounded once, just before upload
}

Per-mode proposed defaults:

ModerefZoomslopePerOctaveMin scaleMax scaleDirection
2D (FOV in deg) 30° +0.12 1.00 1.45 Grow when zooming in, never shrink below base
3D (AU) 15 000 AU −0.18 0.30 1.00 Shrink when zooming out, never grow above base

Note the sign flip: in 3D octaves > 0 means zoomed closer than ref and we want size = base, so slope is negative. Equivalently we can split out the sign and compute octavesOut = log2(zoom / refZoom); the math is the same.

3.3 Implementation footprint

Two-file change, all inside the existing drawDots hot path:

  • src/exoplanet-renderer.ts — replace the five-line block at 787-791 with the §3.1 helper. The surrounding gl.uniform1f(_uPixelScale, sizeForMode * dpr) line stays the same; only the way sizeForMode is computed changes.
  • Per-mode config (refZoom, slope, min/max) lives as module-level consts at the top of exoplanet-renderer.ts so they’re findable and tuneable in one place. Optional window.__markerScaleDebug = true would log {zoom, octaves, scale, sizeFinal} per frame for in-browser tuning.
  • No call-site changes — the rest of the renderer already treats sizeForMode as opaque CSS px.

3.4 Reversion strategy

The new helper sits between the existing constants and gl.uniform1f. To revert, restore the five-line a + b·ln(zoom) block and delete the helper plus the module-level config consts. No engine patches, no schema changes.

3.5 Edge cases worth flagging

  • Mode switch during a slew. renderContext.viewCamera.zoom can transiently be in the middle of an interpolation. The helper is stateless, so it just produces the right size for whatever zoom is current — no special handling needed.
  • Per-device base vs. zoom adaptation interaction. Mobile 3D base is already 1 px so the shrink-on-zoom-out behavior is mostly invisible there. If we want the effect to be perceptible on mobile, we’d bump the 3D mobile base back to 2 px and let the formula scale it down. That contradicts §1.2’s recent change — flagged for your call.
  • The Math.round. Today’s code rounds once. New code should also round once (after the multiply) to avoid flicker between adjacent integer sizes during smooth zooms. The shader accepts a float, so rounding is purely cosmetic; we could also drop it entirely to get sub-pixel sizes (anti-aliased dots look smoother under continuous zoom).

3.6 Open questions for approval

  1. Are the §3.1 slope & clamp values in the right ballpark, or do you want more / less dramatic change?
  2. For 3D mobile: keep the new 1-px base (subtle shrink) or restore 2-px base (more visible shrink curve)?
  3. Drop the integer round for smoother sub-pixel transitions, or keep it (sharper but quantized)?
